# 아키텍처 패턴 및 설계 원칙

## 아키텍처 패턴
### 1. 레이어드 아키텍처
- **Controller Layer**: HTTP 요청/응답 처리
- **Service Layer**: 비즈니스 로직 구현
- **Repository Layer**: 데이터 접근 추상화
- **Database Layer**: Prisma ORM을 통한 데이터 영속성

### 2. 모듈 기반 설계
- **기능별 모듈 분리**: Inventory, Database, RabbitMQ
- **의존성 주입**: NestJS DI 컨테이너 활용
- **전역 모듈**: @Global() 데코레이터로 공통 모듈 관리

## 동시성 제어 패턴
### 1. 낙관적 락 (Optimistic Locking)
- **구현**: Prisma version 필드 활용
- **적용**: 충돌이 적은 환경
- **장점**: 성능 우수, 데드락 없음
- **단점**: 충돌 시 재시도 필요

### 2. 비관적 락 (Pessimistic Locking)
- **구현**: SELECT FOR UPDATE 쿼리
- **적용**: 데이터 일관성이 중요한 환경
- **장점**: 강한 일관성 보장
- **단점**: 성능 오버헤드, 데드락 가능성

### 3. 분산 락 (Distributed Locking)
- **구현**: Redis 기반 UUID 락
- **적용**: 마이크로서비스 환경
- **장점**: 서비스 간 동시성 제어
- **단점**: 네트워크 의존성, 복잡성

## 에러 처리 패턴
### 1. 구조화된 에러 응답
- **HttpException**: 일관된 에러 구조
- **상태 코드**: HTTP 표준 준수
- **메시지**: 한글 사용자 친화적 메시지

### 2. 재시도 패턴
- **지수 백오프**: 재시도 간격 증가
- **최대 재시도**: 무한 루프 방지
- **랜덤 지터**: 동시 재시도 방지

## 캐싱 패턴
### 1. 읽기 전용 캐시
- **Cache-Aside**: 애플리케이션 제어 캐싱
- **TTL**: 5분 캐시 만료
- **무효화**: 업데이트 시 캐시 삭제

### 2. 네임스페이스 분리
- **cache**: 데이터 캐싱
- **session**: 세션 관리

## 데이터베이스 패턴
### 1. Repository 패턴
- **Base Repository**: 공통 기능 추상화
- **Specific Repository**: 도메인별 구현
- **헬스체크**: 연결 상태 모니터링

### 2. 트랜잭션 관리
- **Prisma Transaction**: ACID 보장
- **비즈니스 트랜잭션**: 서비스 레벨 관리
